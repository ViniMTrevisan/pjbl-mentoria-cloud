1. Introdução e metas

O Veterano. conecta calouros a veteranos para sessões de mentoria acadêmica. O calouro busca mentores, solicita uma sessão e avalia depois; o veterano publica áreas e horários e aceita ou recusa solicitações. Um mesmo usuário pode ser mentor e mentorado.

Esta entrega implementa a arquitetura distribuída do PJBL: microfrontends, BFF, dois microsserviços com bancos diferentes, uma Azure Function e um API Gateway. O código roda completo em docker compose e as mesmas imagens são publicadas no Docker Hub.

3. Contexto e escopo

3.1 Contexto de negócio

3.2 Contexto técnico

O navegador baixa o shell e os dois remotes (Module Federation). Toda chamada de dados passa pelo API Gateway, que encaminha ao BFF. O BFF agrega Serviço de Mentores (MongoDB), Serviço de Sessões (Azure SQL) e Azure Function (reputação). O navegador nunca fala com um serviço interno, e nenhum serviço lê o banco de outro.

Parceiro Protocolo Observação
Navegador → Gateway HTTPS/JSON header X-Usuario-Id (identidade simulada)
Gateway → BFF HTTP interno remove /api, aplica CORS e rate limit
BFF → serviços HTTP/JSON timeout de 3 s, agregação tolerante a falha
Serviço de Mentores → MongoDB wire protocol/TLS driver oficial, conexão cacheada
Serviço de Sessões → Azure SQL TDS 1433 mssql, transação + rowversion
Serviço de Sessões → Function HTTP eventos do outbox, pelo menos uma vez

5.2 Nível 2 — componentes (C4 nível 3)

5.2.1 Microfrontends

O shell é dono das rotas e do usuário atual. Os remotes não se importam entre si: conversam por URL e por CustomEvent (veterano:sessoes-atualizadas). React é shared singleton para não carregar duas cópias. Falha ao baixar um remote é contida por ErrorBoundary.

5.2.2 API Gateway e BFF

O BFF não tem banco e não contém regra de negócio. GetAggregatedData chama os três dependentes em paralelo com timeout de 3 s, usa Promise.allSettled e devolve parcial e falhas. O gateway concentra CORS, limite de 120 req/min por IP e o carimbo X-Gateway.

5.2.3 Serviço de Mentores

Fatias: createMentor, listMentores, getMentor, updateMentor, deleteMentor, addAvaliacao. O domínio é puro e concentra validação, normalização de busca, campos alterados e inclusão de avaliação. O adaptador Mongo e o adaptador em memória implementam a mesma porta MentorRepository; o segundo permite rodar e testar sem Docker.

5.2.4 Serviço de Sessões

A transição de estado acontece em uma transação: UPDATE ... WHERE id AND status_esperado garante que dois cliques concorrentes não vençam; a linha de OUTBOX_EVENTO entra na mesma transação. Um relay a cada 2 s publica os pendentes e marca publicado_em.

6. Visão de runtime

6.1 Agregação de tela

6.2 Solicitar e aceitar sessão

  1. Calouro escolhe mentor e horário no MFE Descoberta; POST /api/sessoes chega ao BFF e ao Serviço de Sessões.
  2. O serviço valida (participantes diferentes, data futura, assunto) e grava SOLICITADA + evento SessaoSolicitada no outbox.
  3. O relay publica o evento na Function; o MFE Agenda recarrega ao receber o evento de UI.
  4. Mentor abre o MFE Agenda e aceita: PATCH /api/sessoes/:id/status com {acao:"aceitar"}. Se o ator não for o mentor → 403; se o estado não for SOLICITADA → 409.

6.3 Ciclo de vida da sessão

6.4 Avaliação e reputação

Somente o mentorado avalia, somente em CONCLUIDA, e uma vez por sessão. A avaliação é gravada no documento do mentor com sessaoId único (409 em duplicidade). A média não é persistida: a Function calcula {media, total, distribuicao, selo} a partir das notas, e o BFF enriquece a lista em uma chamada por mentor.

8. Conceitos transversais

8.1 Eventos

Envelope no estilo CloudEvents (id, type, source, time, data). O id é a chave de idempotência: a Function ignora um evento repetido. Em nuvem o mesmo envelope vai ao Service Bus com sessionId = sessaoId para preservar a ordem dos eventos da mesma sessão.

8.2 Dados

Banco Entidades Modelagem
MongoDB mentores documento único com areas, disponibilidades, avaliacoes; índice único em id
Azure SQL SESSAO, OUTBOX_EVENTO status + rowversion; outbox na mesma transação
Function buffer em memória apenas demonstração; alvo é Service Bus + Table Storage

Referências entre serviços são identificadores, nunca chaves estrangeiras.

8.3 Segurança

  • Gateway é a única porta de entrada do navegador.
  • Serviços internos não são expostos ao navegador no desenho alvo (apenas o BFF os alcança).
  • Header X-Usuario-Id simula identidade; não é autenticação e está registrado como dívida.
  • Segredos em .env, fora do repositório; .env.example versionado.
  • Erros 500 não devolvem mensagem do driver nem stack.

8.4 Validação e erros

Código Quando
400 JSON malformado ou id inválido
403 ator não participa ou não é mentor na ação
404 recurso inexistente
409 transição inválida, avaliação duplicada ou concorrência
422 regra de validação (nota fora de 1..5, data passada, campos)
502 proxy do BFF não alcançou o serviço
200 + parcial agregação com dependência fora

8.5 Observabilidade

Cada serviço loga operação, status e duração sem dado pessoal. /health existe em todos os contêineres e é usado pelos healthcheck do Compose; o /health do BFF informa o estado dos três dependentes. Em nuvem, Application Insights recebe as mesmas informações.

8.6 Contratos entre microfrontends

Rotas pertencem ao shell; remotes recebem apenas o necessário por props e leem o usuário do localStorage. A comunicação indireta usa CustomEvent. Tokens CSS ficam no shell.

9. Decisões de arquitetura (ADRs)

ADR-01 — Microfrontends com Module Federation. Contexto: 4 alunos mexem no front ao mesmo tempo. Decisão: shell + remotes compostos no navegador. Consequência: deploy independente; custo de compatibilidade de React e fallback obrigatório.

ADR-02 — Kong local, APIM no alvo. Contexto: CORS/rate limit/rota se repetiriam. Decisão: gateway dedicado. Consequência: uma porta de entrada e um salto extra; o alvo troca Kong por APIM sem tocar no BFF.

ADR-03 — BFF sem regra de negócio. Contexto: telas precisam de dados de três origens. Decisão: agregação e adaptação de formato no BFF. Consequência: uma chamada por tela; risco de virar gargalo se acumular regra — proibido por convenção.

ADR-04 — Banco poliglota por serviço. Contexto: perfil é documento, sessão é transação. Decisão: MongoDB e Azure SQL, sem acesso cruzado. Consequência: sem junção; leitura cruzada via BFF; duas tecnologias para operar.

ADR-05 — Reputação na Function. Contexto: cálculo simples, precisa de exemplo de serverless com contrato próprio. Decisão: HTTP trigger puro e testável. Consequência: uma chamada extra por mentor na agregação, mitigada por paralelismo e limite de concorrência.

ADR-06 — Outbox em vez de transação distribuída. Contexto: gravar sessão e publicar evento. Decisão: outbox na mesma transação + relay. Consequência: pelo menos uma vez; consumidor precisa ser idempotente.

11. Riscos e dívidas técnicas

Risco / dívida Impacto Mitigação
Identidade simulada por header qualquer cliente pode se passar por outro usuário documentado; alvo é Entra External ID + JWT no gateway
Sink de eventos em memória eventos não sobrevivem a restart outbox garante reenvio; alvo é Service Bus
Sem e-mail real (RF8) notificação apenas registrada Interface de e-mail prevista; alvo ACS
Cold start em cadeia primeira requisição lenta em nuvem imagens leves e, no alvo, instância mínima no BFF
Banco SQL em emulador diferenças em relação ao Azure SQL T-SQL padrão e migração por DDL simples
Duplicação do cliente HTTP nos MFEs manutenção em três lugares pacote compartilhado é evolução prevista
Sem CI/CD nesta entrega publicação manual scripts publish:dockerhub e smoke versionados

12. Roteiro de demonstração

  1. cp .env.example .env && docker compose up --build -d; aguardar todos os healthchecks.
  2. Abrir http://localhost:3000 com o usuário Bruno Calouro.
  3. Dashboard mostra KPIs, próximas sessões e top mentores vindos de /aggregated-data.
  4. Ir em Mentores, filtrar por matéria, abrir um perfil e solicitar sessão em um horário.
  5. Trocar para Ana (mentora) e abrir Sessões: aceitar a solicitação.
  6. Trocar de volta para Bruno, concluir a sessão e avaliar com nota e comentário.
  7. Voltar aos mentores: a reputação atualizada aparece no card.
  8. Abrir Swagger do BFF, dos dois serviços e a Admin API do Kong.
  9. Derrubar sessoes-service e recarregar o dashboard: resposta parcial, sem tela em branco.
