1. Introdução e Objetivos

Veterano. é uma plataforma web que conecta calouros que precisam de ajuda em uma matéria a veteranos dispostos a dar mentoria. Hoje esse encontro acontece de forma informal — grupos de WhatsApp, indicação pessoal, sorte — e depende de o calouro já conhecer alguém. O sistema cobre o fluxo inteiro: cadastro → descoberta → agendamento → notificação → avaliação.

Construção incrementalMonólito modular primeiro, extração depoisAs costuras dos serviços já existem no código como fatias e portas; extrair é mover pastas e trocar a chamada local por HTTP ou evento.
Comunicação síncronaSó na leitura (BFF → serviços)Leituras precisam de resposta imediata. Escritas que afetam outro serviço viram evento.

5.2.2 API Gateway e BFF Web

{{DIAGRAMA:c4-n3-bff-gateway|C4 Model — Nível 3 (Componentes) do API Gateway e do BFF Web. As políticas do gateway executam em ordem antes de chegar ao BFF.}}

O gateway resolve o que é igual para toda rota (quem é o usuário, quanto ele pode chamar, de qual origem) e o BFF resolve o que é específico de cada tela (quais serviços chamar e como juntar as respostas). O BFF não tem banco nem regra de negócio: se um serviço não responder em 3 s, devolve a parte que obteve e sinaliza o campo ausente, em vez de falhar a tela inteira.

5.3 Nível 3 — código (C4 Nível 4)

5.3.1 Clean Architecture e Vertical Slice no código entregue

O back-end entregue (api/src) combina os dois estilos. A Clean Architecture define camadas e a regra de que dependências só apontam para dentro; o Vertical Slice define que cada caso de uso é um arquivo próprio que atravessa essas camadas, em vez de existir um “service” genérico com todos os métodos.

api/src/
├── functions/              ← adaptadores de entrada (Azure Functions) — camada externa
│   ├── mentores.js           GET /mentores, GET /mentores/{id}
│   ├── sessoes.js            GET /sessoes
│   ├── mentoresInserir.js    POST   /mentores-db
│   ├── mentoresPesquisar.js  GET    /mentores-db
│   ├── mentoresAlterar.js    PUT|PATCH /mentores-db/{id}
│   ├── mentoresExcluir.js    DELETE /mentores-db/{id}
│   ├── health.js             GET /health
│   ├── http.js               json(), lerCorpo(), executarCasoHttp()
│   └── dependencies.js       raiz de composição: cria e injeta os adaptadores
├── features/               ← aplicação: uma fatia por caso de uso
│   ├── mentors/  listPublicMentors · getPublicMentor · createMentor
│   │             searchMentors · updateMentor · deleteMentor
│   └── sessions/ listSessions
├── domain/mentor.js        ← regras puras: calcularReputacao, validarMentor, novoMentor, camposAlterados
├── ports/                  ← contratos exigidos pelas fatias
│   ├── MentorRepository.js
│   └── CatalogoMentores.js
├── infrastructure/         ← adaptadores de saída
│   ├── mongo/  MongoMentorRepository.js · client.js
│   └── mock/   MockMentorCatalog.js
└── data/mock.js            ← fixtures, sem lógica

Regra de dependência, verificável no código: domain/mentor.js não importa nada; as fatias importam só o domínio e recebem portas como parâmetro; apenas infrastructure/mongo importa o pacote mongodb; apenas functions/ importa @azure/functions. Quem liga as peças é dependencies.js, na borda. A figura a seguir mostra as fatias (colunas) cruzando as camadas (faixas).

6.2 Cenário alvo: solicitar e aceitar uma sessão (RF6, RF7, RF8)

  • O gateway barra antes. Token inválido ou excesso de chamadas é recusado no APIM, sem executar função.
  • A regra fica no dono. Só o Serviço de Sessões decide se o horário é válido (422) e se o ator pode aceitar (403).
  • Gravar e avisar não dependem um do outro. A sessão e o evento entram no banco na mesma transação (outbox); o relay publica depois. Se o Service Bus cair, a sessão já existe e o evento sai quando ele voltar.
  • O consumidor é idempotente. Entrega “pelo menos uma vez” pode repetir a mensagem; o Serviço de Notificações descarta o messageId já processado.

A requisição do calouro termina no passo do COMMIT: a partir daí, a notificação é trabalho assíncrono e não afeta o tempo de resposta nem o resultado da solicitação.

8. Conceitos Transversais

8.1 Arquitetura orientada a eventos

Toda comunicação assíncrona entre serviços passa por um único tópico do Service Bus. Cada consumidor tem sua assinatura com filtro, então recebe só os tipos de evento que lhe interessam e falha sem afetar os demais.

  • Envelope: CloudEvents 1.0 (id, type, source, time, data). O id vira messageId no Service Bus e é a chave de idempotência.
  • Garantia: pelo menos uma vez. O outbox impede perder evento; o consumidor idempotente impede efeito duplicado.
  • Ordem: eventos da mesma sessão usam sessionId = sessaoId, preservando a ordem SOLICITADA → ACEITA → CONCLUIDA.
  • Falha: após 5 tentativas a mensagem vai para a dead-letter da assinatura, com alerta no Application Insights.
  • Evolução: campos só são adicionados; remover ou mudar significado exige novo type (SessaoAceita.v2).

8.3 Serverless

  • Sem estado em memória. Nenhuma função guarda dado entre invocações; o único cache é a conexão com o MongoDB (criarProvedorColecao), que reabre sozinha se cair.
  • Escala a zero. Functions Flex, APIM Consumption e bancos serverless não cobram ociosidade relevante; Azure SQL pausa sozinho.
  • Cold start em cadeia. Gateway → BFF → serviço podem acordar em sequência. Mitigação: Flex Consumption e, se medido como problema, uma instância sempre pronta só no BFF.
  • Gatilhos como contrato. HTTP para leitura e comando; Service Bus para eventos; Timer para o relay do outbox.

8.4 Segurança

  • Autenticação no gateway. validate-jwt confere assinatura, emissor e audiência do Entra antes de qualquer função; o BFF recebe o usuário em cabeçalho definido pelo gateway.
  • Autorização no dono do dado. Só o Serviço de Sessões sabe se o usuário participa da sessão; resposta 403 caso contrário.
  • Serviços internos fechados. Function Apps dos serviços aceitam apenas o BFF (chave de função ou restrição de acesso), nunca o navegador.
  • Segredos fora do código. MONGODB_URI em configuração da Function App hoje; Key Vault com Managed Identity no alvo.
  • Estado atual. Endpoints ainda anônimos (authLevel: anonymous) e CORS restrito à origem do Static Web App e a localhost:5173 — registrado como dívida.

8.5 Validação e tratamento de erros

  • Validação de domínio em validarMentor (completa na criação, parcial na alteração).
  • Códigos: 400 payload ou id inválido; 404 inexistente; 500 falha de infraestrutura, sem a mensagem do driver; no alvo, 403 ator sem permissão e 422 violação de regra de negócio.
  • Toda tela trata carregando, vazio e erro; nunca tela em branco.

8.6 Observabilidade

Application Insights em todas as Function Apps. O cabeçalho W3C traceparent é propagado do gateway ao BFF e aos serviços, e copiado para as propriedades da mensagem no Service Bus, permitindo ver uma solicitação de sessão e a notificação que ela gerou na mesma transação distribuída. Logs registram operação e filtros, sem dado pessoal.

8.7 Contratos entre microfrontends

Os MFEs não se importam entre si: comunicam-se pela URL (rotas) e por eventos de navegador (CustomEvent no window) quando necessário. React, React Router e o pacote de API são shared singletons. Estilo visual vem de tokens CSS do Shell (index.css), para que os remotes pareçam um único produto.

8.8 Uso de IA generativa

Front-end, Functions, reorganização em fatias e esta documentação foram produzidos com assistência do Claude Code (com Azure MCP e Azure CLI). Prompts versionados em Prompt.md e docs/TDE2-PROMPTS.md. Todo código passou por revisão humana: regras conferidas contra o PRD, endpoints testados e telas navegadas no ambiente publicado.

9. Decisões de Arquitetura

Registradas no formato ADR. Entram as decisões caras de tomar ou de reverter.

ADR-01 — Microfrontends com Module Federation, extraídos de um monólito modular

Contexto
Quatro alunos trabalham no front-end ao mesmo tempo; o Static Web Apps só serve arquivos estáticos.
Decisão
Shell + três remotes compostos no navegador por Module Federation (@originjs/vite-plugin-federation). Construir primeiro como SPA única com uma pasta por área e extrair cada pasta quando a fronteira estiver estável.
Consequências
+ deploy independente por área; fronteira de MFE igual à de serviço. − versões de React precisam ser compatíveis entre remotes; uma falha de carga de remote precisa de fallback no Shell.
Alternativas
iframes (isolamento forte, UX ruim); composição no servidor (incompatível com SWA estático).

ADR-02 — Azure API Management Consumption como API Gateway

Contexto
Autenticação, limite de chamadas e CORS se repetiriam em cada Function App.
Decisão
APIM no tier Consumption na frente do BFF, com políticas validate-jwt, rate-limit-by-key e cors.
Consequências
+ preocupações transversais em um lugar; serverless, com cota gratuita mensal. − mais um salto de rede e um cold start próprio.
Alternativas
Roteamento do próprio SWA (sem JWT nem rate limit configuráveis); Application Gateway (não é serverless, custo fixo).

ADR-03 — Um BFF para a Web

Contexto
As telas precisam de dados de vários serviços; só existe um tipo de cliente (navegador).
Decisão
Um único BFF Web em Functions, um endpoint por tela, sem banco e sem regra de negócio.
Consequências
+ navegador faz uma chamada por tela; serviços ficam com contratos genéricos. − o BFF pode virar gargalo de mudanças se acumular lógica — regra: lógica de negócio nunca entra no BFF. Um app mobile futuro teria seu próprio BFF.

ADR-04 — Microsserviços por subdomínio, com banco próprio e poliglota

Contexto
Mentores, Sessões, Avaliações e Notificações têm dados de formas diferentes e mudam por motivos diferentes.
Decisão
Quatro serviços, cada um dono do seu banco: documento (Mentores), relacional (Sessões), NoSQL serverless (Avaliações), chave-valor (Notificações). Nenhum serviço acessa banco alheio.
Consequências
+ deploy, escala e falha isolados; cada dado no armazenamento que lhe cabe. − sem junção entre serviços; consultas cruzadas via BFF ou projeção; quatro tecnologias de dados para operar.

ADR-05 — Service Bus com tópico único e outbox transacional

Contexto
Notificação e reputação precisam acontecer depois de uma escrita em outro serviço, mesmo que o consumidor esteja fora.
Decisão
Tópico veterano.eventos no Service Bus Standard, uma assinatura filtrada por consumidor; produtores com outbox e relay; consumidores idempotentes.
Consequências
+ entrega garantida, dead-letter, ordenação por sessão, retentativa automática. − custo fixo mensal do tier Standard; consistência eventual visível ao usuário.
Alternativas
Event Grid (mais barato, sem sessões/ordenação); Storage Queue (sem publicação para vários consumidores).

ADR-06 — Reputação como projeção atualizada por evento

Contexto
Na versão 1, a reputação era calculada lendo as avaliações. Com Database per Service, o Serviço de Mentores não pode ler o banco de Avaliações.
Decisão
O Serviço de Mentores mantém REPUTACAO_PROJECAO, recalculada a cada AvaliacaoRegistrada com a mesma função calcularReputacao que já existe no domínio. Substitui o ADR-04 da versão 1.
Consequências
+ busca rápida, sem chamada a outro serviço. − atraso de segundos entre avaliar e ver a nova média.

ADR-07 — Clean Architecture com Vertical Slice dentro de cada serviço

Contexto
Os handlers originais misturavam HTTP, regra e acesso a dados; a troca de mock por MongoDB exigiria reescrevê-los.
Decisão
Um arquivo por caso de uso em features/; regras em domain/; contratos em ports/; implementações em infrastructure/; Azure Functions só em functions/; composição em dependencies.js.
Consequências
+ caso de uso fácil de achar e mudar; domínio testável sem Azure nem banco; extração de serviço = mover fatias. − mais arquivos; pequena duplicação entre fatias parecidas, aceita para não acoplá-las.

ADR-08 — Flex Consumption em vez de Consumption clássico

Contexto
A Function App em Consumption Linux respondia 503 até no SCM; o plano tem fim de suporte anunciado.
Decisão
Flex Consumption com Node 22 para todas as Function Apps.
Consequências
+ subiu na primeira tentativa, cold start menor. − publicação por config-zip, pois az functionapp deploy responde 415.

ADR-09 — MongoDB Atlas como banco do Serviço de Mentores

Contexto
A entrega de CRUD pedia persistência real; o perfil de mentor é um documento com listas aninhadas.
Decisão
MongoDB Atlas M0, acessado pelo driver oficial atrás da porta MentorRepository.
Consequências
+ gratuito, modelo de documento natural para o perfil. − sai do catálogo Azure; limites do M0. Migrar para Cosmos DB for MongoDB troca só a URI, pois o protocolo é compatível.
