1. Introdução e Objetivos

Veterano. é uma plataforma web que conecta calouros que precisam de ajuda em uma matéria a veteranos dispostos a dar mentoria. Hoje esse encontro acontece de forma informal — grupos de WhatsApp, indicação pessoal, sorte — e depende de o calouro conhecer alguém. O sistema resolve o fluxo completo de ponta a ponta: cadastro → descoberta → agendamento → avaliação.

4.1 Software Architecture Canvas

Contexto e problema
  • Calouros não têm canal estruturado para tirar dúvidas de matéria nem orientação de trajetória.
  • Veteranos dispostos a ajudar não têm onde se oferecer, controlar disponibilidade ou acumular reputação.
  • O encontro hoje depende de rede pessoal e sorte, e é invisível para a coordenação.
Objetivos de negócio
  • Reduzir a evasão nos primeiros períodos.
  • Dar visibilidade ao veterano que ajuda.
  • Tornar a mentoria mensurável para a coordenação.
Usuários e stakeholders
  • Calouro (mentorado) — usuário primário.
  • Veterano (mentor) — oferta.
  • Coordenação — moderação e métricas.
  • Equipe de 4 alunos, um semestre.
Requisitos-chave
  • RF5 descoberta com filtros.
  • RF6/RF7 solicitação e resposta.
  • RF9/RF12 agenda e ciclo de vida.
  • RF10/RF11 avaliação e reputação.
  • RF8 notificação a cada transição.
Atributos de qualidade
  • Usabilidade no celular.
  • Autorização por recurso.
  • Degradação suave do e-mail.
  • Custo dentro do crédito.
  • Regra testável fora da UI.
Restrições
  • Azure obrigatório.
  • Static Web Apps + Functions.
  • Assinatura de estudante.
  • brazilsouth bloqueada por policy.
  • Repositório público — zero segredos.
Princípios
  • Regra de negócio no servidor.
  • Serviços gerenciados antes de infraestrutura própria.
  • Escalar a zero por padrão.
  • Complexidade só com requisito que a pague.
  • Estado terminal não volta atrás.
Decisões estruturais
  • SPA estática, sem SSR.
  • API HTTP stateless em Functions.
  • PostgreSQL relacional gerenciado.
  • Fila entre a API e o e-mail.
  • Identidade delegada ao Entra.
Componentes
  • SPA React (3 telas).
  • API de Mentoria (HTTP triggers).
  • Núcleo de domínio (sessão, reputação).
  • Processador de notificações.
  • Repositórios de dados.
Tecnologias
  • React 19, Vite, TypeScript.
  • Azure Functions v4, Node 22.
  • Azure Static Web Apps (Free).
  • PostgreSQL Flexible Server.
  • Zod, Application Insights.
Riscos
  • Latência de centralus ao Brasil.
  • Cold start na primeira chamada.
  • Crédito de estudante esgotar.
  • Mock ainda no lugar do banco.
  • Autenticação não implementada.
Métricas de sucesso
  • Produto: o roteiro completo do MVP (cadastrar → publicar disponibilidade → buscar → solicitar → aceitar → concluir → avaliar → ver reputação) executa de ponta a ponta na aplicação publicada.
  • Arquitetura: busca de mentores responde em até 2 s no P95; falha de e-mail não gera erro HTTP; nenhum acesso a sessão de terceiro passa pela autorização.
  • Operação: custo mensal dentro do crédito Azure for Students; toda exceção não tratada visível no Application Insights.

5.3.1 Diagrama de classes (UML)

{{DIAGRAMA:c4-n4-classes}}

O modelo segue a regra do PRD de não separar mentor e mentorado em entidades distintas: há uma única classe Usuario, com os papéis representados pelos atributos ehMentor e ehMentorado, e a Sessao se liga a ela por dois relacionamentos de papéis diferentes. 6. Visão de Runtime

Como os blocos de construção colaboram em tempo de execução. O cenário escolhido é o caminho crítico do produto — solicitar e responder uma sessão — porque é onde vivem a autorização, a máquina de estados e a notificação.

6.1 Cenário: solicitar e aceitar uma sessão (RF6 e RF7)

Três aspectos do cenário merecem destaque, e aparecem no diagrama a seguir:

  • A validação acontece duas vezes, em camadas diferentes. O ValidadorZod rejeita o payload malformado (400); o ServicoDeSessao rejeita o payload bem formado mas inválido no domínio — horário fora da disponibilidade ou no passado (422).
  • A autorização é do ator, não da rota. Só o mentor daquela sessão específica pode aceitar. Um mentorado tentando aceitar a própria solicitação recebe 403, mesmo estando autenticado.
  • O e-mail sai do caminho síncrono. A API enfileira e responde. Se a fila ou o serviço de e-mail estiver fora do ar, a sessão já foi criada e a notificação in-app já existe.

7.2 Escolha de região

Todos os recursos estão em centralus. Essa não foi a primeira escolha: brazilsouth seria a região mais próxima do usuário final, mas a policy Allowed resource deployment regions da assinatura Azure for Students a bloqueia. 8. Conceitos Transversais

8.1 Modelo de domínio e persistência — Diagrama de Entidades e Relacionamentos

{{DIAGRAMA:der}}

8.2 Segurança

  • Autenticação delegada. A identidade fica no Entra External ID. A API valida a assinatura do token contra o JWKS do provedor e nunca guarda senha. Enquanto o provedor não está integrado, os endpoints publicados são de leitura sobre dados fictícios e ficam com authLevel: anonymous.
  • Autorização por recurso. Estar autenticado não basta: cada operação verifica se o usuário é o mentor ou o mentorado daquela sessão. Tentativa de acesso a sessão de terceiro responde 403.
  • Segredos fora do repositório. O repositório é público. Connection strings e chaves ficam em configuração de aplicação e, na evolução, no Key Vault acessado por Managed Identity — sem credencial no código.
  • CORS restritivo. A Function App aceita apenas a origem do Static Web App e http://localhost:5173, em vez do curinga *.
  • Senha (caso a autenticação própria seja retomada). Hash bcrypt, nunca em texto plano e nunca em log.

8.3 Validação e tratamento de erros

  • Os mesmos schemas Zod validam no formulário e no servidor. A validação no cliente é conveniência; a do servidor é a que vale.
  • Códigos de resposta com significado consistente: 400 payload malformado, 403 ator sem permissão sobre o recurso, 404 recurso inexistente, 422 payload válido mas proibido pela regra de negócio.
  • Toda tela trata três situações além do caminho feliz: carregando, vazio e erro. Nenhuma falha de rede resulta em tela branca — a interface explica o que houve, na voz do sistema.

8.4 Internacionalização e formatação

Interface inteiramente em pt-BR. Datas em dd/MM/yyyy e horários no fuso America/Sao_Paulo, formatados com Intl.DateTimeFormat no cliente a partir de timestamps com fuso vindos da API — o servidor nunca envia data já formatada.

8.5 Observabilidade

Application Insights coleta requisições, dependências e exceções da Function App. Cada handler registra a operação e os filtros recebidos, sem incluir dado pessoal no log. Falhas de envio de e-mail são registradas como aviso, não como erro da requisição — coerente com o tratamento best effort descrito na seção 4.

8.6 Experiência e interface

O front-end é responsivo com abordagem mobile first, porque o calouro abre o sistema no celular entre uma aula e outra. A identidade visual parte do mundo do aluno — papel quadriculado e marca-texto — e reserva a cor de destaque para uma única informação: o que está disponível. O elemento de maior peso visual é a grade semanal de disponibilidade do mentor, desenhada como a grade horária da faculdade. Foco de teclado visível e prefers-reduced-motion respeitado.

8.7 Uso de IA generativa

O front-end, as Azure Functions e os scripts de infraestrutura foram gerados com assistência do Claude Code, com acesso ao Azure MCP Server e à Azure CLI. Os prompts estão versionados em Prompt.md, no repositório. Todo código gerado passou por revisão humana antes da publicação: conferência das regras de negócio contra o PRD, teste dos endpoints e navegação nas três telas no ambiente publicado.

9. Decisões de Arquitetura

Decisões registradas no formato ADR. Só entram aqui as que foram custosas de tomar ou que seriam caras de reverter.

ADR-01 — Substituir o Next.js full-stack por SPA estática mais API serverless

Contexto
O PRD original previa Next.js com App Router, Route Handlers e SSR em um único projeto, publicado na Vercel. A disciplina exige Azure, e a atividade exige Azure Static Web Apps com Azure Functions.
Decisão
Separar em dois artefatos: uma SPA React + Vite puramente estática e uma API em Azure Functions.
Consequências
Positivas: o front-end vira arquivo estático, servido pela borda a custo próximo de zero; front-end e API escalam e são publicados de forma independente; o contrato entre eles fica explícito. Negativas: perdemos SSR e Server Actions, o que piora o SEO (irrelevante aqui, já que o conteúdo é autenticado) e obriga a tratar estados de carregamento manualmente em cada tela.
Alternativas descartadas
Next.js com adaptador para Static Web Apps (SSR híbrido) — mais partes móveis do que a equipe conseguiria operar no semestre.

ADR-02 — Flex Consumption em vez de Consumption clássico

Contexto
A Function App criada no plano Consumption em Linux respondia HTTP 503 em todos os endpoints, inclusive no site de deploy (SCM), sem que o host chegasse a iniciar. O plano também tem fim de suporte anunciado.
Decisão
Recriar a Function App em Flex Consumption com Node 22.
Consequências
Positivas: a aplicação subiu na primeira tentativa; cold start menor e plano com suporte de longo prazo. Negativas: o comando az functionapp deploy não funciona nesse plano (responde 415) — a publicação usa az functionapp deployment source config-zip, o que precisa estar documentado para quem for publicar depois.

ADR-03 — Function App separada, e não as managed functions do Static Web App

Contexto
O Static Web Apps permite hospedar funções na pasta /api do próprio site, o que dispensaria configurar CORS e um segundo recurso.
Decisão
Manter a API como Function App independente.
Consequências
Positivas: a API tem URL pública própria e pode ser consumida por outros clientes; escala e é publicada separadamente do front-end; a entrega da disciplina exige o endereço da Azure Function. Negativas: exige configurar CORS explicitamente e gerenciar mais um recurso.

ADR-04 — Reputação calculada na leitura, sem coluna materializada

Contexto
A reputação (RF11) aparece na busca e no perfil, e muda a cada avaliação nova. Guardá-la em coluna evitaria a agregação.
Decisão
Calcular por agregação na leitura, sem persistir.
Consequências
Positivas: nenhuma invalidação de cache, nenhum risco de divergência entre a média exibida e as notas reais. Negativas: a consulta de busca agrega em toda leitura — aceitável no volume esperado, e revisável se a listagem crescer.

ADR-05 — Notificação in-app como fonte de verdade, e-mail assíncrono

Contexto
O RF8 pede notificação a cada mudança de status. A entrega de e-mail depende de terceiro e pode falhar ou demorar.
Decisão
Gravar a notificação in-app dentro da transação da transição e enfileirar o e-mail para um processador separado.
Consequências
Positivas: a requisição HTTP não fica presa a um serviço externo; falha de e-mail não vira erro para o usuário; retentativa fica isolada no consumidor da fila. Negativas: mais um contêiner e uma fila para operar, e o e-mail passa a ter latência variável.

ADR-06 — Dados mock dentro das Functions, sem serviço externo de mock

Contexto
A atividade sugeria o Apidog como plataforma de mock. O banco ainda não existe e a API precisa responder dados coerentes.
Decisão
Manter os dados fictícios em um módulo dentro da própria Function App, atrás dos mesmos handlers que atenderão o banco real.
Consequências
Positivas: as regras de negócio (filtro, ordenação, ausência de avaliações) já rodam no servidor e continuam valendo quando o banco entrar; nenhuma dependência de conta em serviço de terceiro; o contrato da API é o definitivo. Negativas: trocar o mock pelo banco exige alterar código, não apenas apontar para outra URL.
